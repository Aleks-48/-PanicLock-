# PanicLock — ITU Hackathon 2026

Демонстрационный мобильный банк для сценария перевода под давлением. Next.js, TypeScript, Tailwind CSS и Lucide React отвечают за интерфейс. FastAPI проверяет PIN и проводит операции в SQLite. Валюта — тенге, суммы вводятся целыми числами. Все счета и получатели учебные.

## Проверка для жюри

[Открыть публичное демо PanicLock](https://paniclock-mobile-banking.vovnoivan.chatgpt.site/). Для проверки достаточно браузера. Выполните оба перевода подряд в одной сессии.

1. Нажмите **Transfer → Continue** с предложенной суммой **500 000 ₸** и введите обычный PIN `1111`. Появится квитанция **Transfer Completed**.
2. Нажмите **Back to home** и повторите тот же перевод с тревожным PIN `9999`. На телефоне снова появится **Transfer Completed**.
3. Включите **SOC view** или откройте [панель SOC](https://paniclock-mobile-banking.vovnoivan.chatgpt.site/soc) во второй вкладке того же браузера. Первая операция отмечена `SETTLED`: получателю зачислено **500 000 ₸**. Вторая отмечена `HOLD_DURESS`: ещё **500 000 ₸** удержаны на 60 минут. События `MOCK_PUSH` и `MOCK_SMS` показывают тестовые уведомления для SOC и доверенного контакта.

4. В **Incident queue** укажите демонстрационное имя оператора. Нажмите **Claim incident**, затем **Cancel transfer & refund**. Удержанные 500 000 ₸ вернутся клиенту. После двух переводов из примера доступный остаток составит **750 000 ₸**, карантин — **0 ₸**. В журнале найдите `INCIDENT_CLAIMED` и `CANCELLED_REFUNDED` с тем же номером операции, именем оператора и серверным временем. Имя вводит участник демо, короткий идентификатор отличает браузеры операторов.

## Регламент SOC после тревожного PIN

Откройте **SOC view → Incident queue → Регламент после тревоги**. Ниже приведён предлагаемый порядок для конкурсного сценария.

1. **Сразу после тревоги.** Нажмите Claim incident. Сверьте номер перевода и время окончания карантина. При признаках непосредственной угрозы сразу передайте случай старшему смены по экстренному порядку банка.
2. **Перед контактом.** Используйте только канал, время и способ обращения, которые клиент заранее указал как безопасные. Если таких указаний нет, дождитесь обращения клиента через официальный канал банка. Для голосовой почты, SMS и обращения к доверенному лицу нужно отдельное согласование с клиентом.
3. **Если клиент ответил.** Начните нейтрально: «Вам удобно сейчас говорить?» Если ответил другой человек, говорить неудобно или связь оборвалась, завершите контакт без упоминания тревоги. Следуйте согласованному плану повторной связи. Перед обсуждением перевода подтвердите личность штатным способом банка. Никогда не запрашивайте PIN, пароль или код из SMS. При подтверждении принуждения отмените удержанный перевод кнопкой Cancel transfer & refund.
4. **Через 60 минут без безопасной связи.** Передайте старшему смены номер операции, время тревоги и результат попыток связи. Зафиксируйте «Безопасность не подтверждена», ответственного и время следующей проверки в рабочем журнале смены. Старший смены ведёт случай до проверки и решает вопрос о дополнительных мерах по правилам банка.

В демо по окончании часа резерв автоматически возвращается в доступный баланс клиента. Получателю деньги не перечисляются. Возврат завершает обработку платежа, но вопрос о безопасности клиента остаётся открытым. Связь с клиентом и передача смене в этом сценарии моделируются устно.

При выборе способа связи учтены рекомендации [Safety Net Project о безопасном контакте](https://www.techsafety.org/safe-contact-methods).

## Локальный запуск через Docker

Из корня репозитория выполните:

```sh
docker compose up --build -d
```

Откройте [мобильный банк](http://localhost:3080) и [экран оператора](http://localhost:3080/soc) в разных окнах. Получите ключ оператора в локальном терминале и вставьте его в поле Operator key:

```sh
docker compose exec -T bank cat /data/judge.key
```

Ключ генерируется при первом запуске. Он хранится в томе базы и в памяти открытой операторской страницы. Клиентский API не выдаёт этот ключ.

1. В мобильном банке нажмите **Transfer**. Оставьте тестового получателя и сумму **500 000 ₸**. Введите **1111**. Получатель получит 500 000 ₸, а доступный баланс отправителя уменьшится с 1 250 000 до 750 000 ₸. Оператор увидит событие SETTLED.
2. Нажмите **Back to home → Reset demo**. Создастся новый учебный счёт с тем же начальным балансом. Записи предыдущего прогона сохранятся в журнале оператора.
3. Повторите перевод с PIN **9999**. На телефоне появится такая же квитанция и тот же остаток. В SOC сумма зачислений останется прежней, карантин увеличится на 500 000 ₸. Новые записи HOLD_DURESS, MOCK_PUSH и MOCK_SMS связаны одним номером перевода. Денежные показатели SOC суммируются по всем учебным сессиям.
4. Обновите страницу или перезапустите контейнеры. Остаток, история платежей и инциденты сохраняются. Операторская страница опрашивает банк раз в секунду. На одном экране панель открывается кнопкой **SOC view**.

**Правило истечения срока.** Через 60 минут с момента тревожного перевода резерв снова доступен отправителю. Обработчик просроченных резервов работает каждые пять секунд и при чтении актуального состояния или следующем платеже. Возврат выполняется однократно, в том числе после простоя сервера. Получатель по этой операции средств не получает.

## Устройство MVP

- `app/page.tsx` — телефон, ввод реквизитов, PIN и единый экран квитанции. `app/client.ts` задаёт типы контрактов.
- `app/observer.tsx`, `app/soc` — авторизованный операторский экран, остаток резерва, сумма зачислений, последние 80 событий и время окончания карантина.
- `backend/main.py` — маршруты FastAPI, сессия устройства в HttpOnly cookie, отдельная авторизация SOC. Демонстрационная сессия открывает собственный счёт. Оба публичных тестовых PIN проверяются по отдельным солёным хешам Argon2id. Пять ошибок блокируют проверку на пять минут.
- `backend/banking.py` — списание доступной суммы, зачисление на учебный счёт получателя или резерв, возврат резерва. Одна транзакция охватывает проводку и журнал. Ключ идемпотентности привязан к отправителю и реквизитам.
- `backend/store.py` — счета, остатки получателей, платежи и события в SQLite. Номер получателя хранится в виде привязанного к счёту хеша и маски. Суммы хранятся как целые KZT.
- Платёжный шлюз эмулируется записью в реестр получателей. Push в SOC и SMS доверенному контакту эмулируются структурированными записями с адресатом, номером операции и временем. Внешние сообщения и обращения в полицию не отправляются.

## Проверки и эксплуатация демо

```sh
docker compose exec bank python -m unittest discover -v
docker compose ps
docker compose down
```

Тесты используют временные базы и управляемые часы. Проверяются квитанции обоих сценариев, зачисление, оповещения, недостаток средств, повтор запросов, конкурентное списание, сохранение резерва после перезапуска и возврат через час.

Compose публикует только интерфейс на loopback. Порт можно выбрать через PANICLOCK_PORT. Данные и ключ SOC переживают обычный docker compose down в именованном томе ledger. Версия предназначена для локальной защиты на синтетических реквизитах. Открытая регистрация демосессий и известные демонстрационные PIN подходят для этой среды. Для банковского пилота потребуются собственные идентификация клиента и операторов, управление ключами и согласованный регламент реагирования.

## Общие автотесты переводов

В корне репозитория выполните `tests/contract/run.sh all` (Bash, Git, Docker, curl и Node.js 24.12+). Один набор из [пяти тестов](tests/contract/transfers.test.mjs) запускается для двух серверных реализаций. Команда поднимает временный контейнер FastAPI с пустой базой и выполняет обработчик Worker из ветки `demo/hosted` с его SQL-миграциями в SQLite в памяти. Для Worker адаптирован интерфейс хранилища D1. Точные секунды задаются только внутри тестовых процессов. SHA проверенного облачного кода выводится в консоль. Для проверки конкретного локального коммита передайте путь к его checkout через `HOSTED_DIR`.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Оба PIN, 500 000 ₸ | Одинаковые поля квитанции и остаток 750 000 ₸. При 1111 получатель получает деньги. При 9999 вся сумма удержана, зачисление равно нулю, в SOC есть тревога и два тестовых уведомления. |
| Две одновременные отмены и повтор | Один ручной возврат в журнале. Резерв равен нулю, остаток клиента ровно 1 250 000 ₸. |
| Отмена через 59 мин 59 с | Оператор успевает отменить перевод. После истечения часа повтор сохраняет результат. |
| Отмена ровно через 60 мин | Резерв истёк. Ручная отмена возвращает HTTP 409, банк учитывает один автоматический возврат. |
| Отмена через 60 мин 1 с | Тот же результат после срока. Получатель ничего не получает. |

Для проверки **опубликованного сайта** выполните `tests/contract/run.sh live`. Режим создаёт отдельные демосессии и проверяет оба PIN и повторный возврат через HTTPS. Три проверки точного времени помечаются как пропущенные в этом режиме. В режиме `all` они обязательны для обеих реализаций.
